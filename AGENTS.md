# BOSS access boundary

Use frozen snapshots, fixtures, and `scripts/run_offline_tests.py` for every coding-agent task in this repository.

For a new HR installation, selected JD setup, or local setup errors, read `docs/hr-quickstart.md`. Coding agents may run `scripts/setup_hr.py init/check` and install declared dependencies; this never permits reading browser credentials or making live requests. `jobs` (including `--refresh` and `--select`) `prepare-job`, and `favorite-close` are human-operated launcher commands. New runs bind one explicit `selected_job_id` and JD hash; multiple open jobs are allowed, with one active run and strictly serial requests. Preserve historical single-job frozen plans without rewriting.

The primary operator workflow is `scripts/run_single_job_live.py configs`, then `start --config <name>`, followed by `status` and one-stage-at-a-time `continue`. `configs` and `status` are local-only and may be used by a coding agent. `start`, `continue`, `close`, legacy `authorize`/`run`, `favorite`, and `clear-circuit` are human-operated; a coding agent must not execute them, sync Chrome login state, or access BOSS through a browser, CDP, Playwright, raw `boss-agent-cli`, or direct HTTP.

`start` and `continue` keep source reads, candidate-detail reads, and local LLM scoring behind separate exact terminal confirmations. One invocation performs at most one external stage. The launcher owns internal one-time authorization IDs and fixed run/output paths; operators do not copy authorization IDs or pass work directories in the primary flow.

When live behavior needs verification, test it with injected clocks, clients, sessions, and temporary guard databases. Do not probe `zhipin.com`.

Every BOSS request must be strictly serial. Do not add threads, async tasks, request pools, pipelining, overlapping transports, or parallel page/detail reads to any live path.

The run config has exactly four controls: `recommendation_source_enabled` (`0` or `1`), `top_priority_search_query_count` (`N`, `0` or greater), `second_page_search_query_count` (`M`, from `0` through `N`, default `0`), and `recent_view_filter` (`include_all` or `exclude_14d`, default `include_all`); `exclude_14d` freezes `viewResume=1`. Per-run recruiter filters are repeatable Chinese `--filter "field=option"` inputs, never extra config fields or raw codes. Only mappings listed by `scripts/search_filters.py list` may be used; freeze canonical selections and `search_filter_params` into the plan and every search operation, and reject drift before transport. Salary omission means unlimited-to-unlimited; cities are limited to the listed popular cities and must bind matching `city` plus `filterParams.region` code/name. Filters apply to all selected search routes and never add requests; recommendation is unaffected. Recommendation is first-page-only. Every selected search route reads page 1; the leading `M` frozen routes additionally read page 2 in route-major order (`route 1 page 1`, `route 1 page 2`, then the next route), strictly serial. Accept every planned page's actual rows and persist each successful page before selecting details; never follow `hasMore`, request page 3, retry, switch to an unplanned source/query, or backfill to reach a card count.

New search-plan generation writes schema V3 directly. It targets 8–12 precise routes; every query is compiled by the program from 2–3 grounded short tokens joined with one ASCII space. Precision gates run before local aggregate history can prioritize unseen combinations, and an honest `generation_shortfall` replaces broad-query padding. Do not add draft, approved, or approval state to generation. Historical V1/V2 plans remain read-only compatible: preserve V1 array order and V2 explicit priority without migration or rewriting.

Candidate-detail requests must come from the persisted candidate pool and a separate exact, single-use detail manifest. Local LLM scoring must consume persisted resumes without creating BOSS requests. Unsupported per-run, rolling-window, or daily request ceilings must not be treated as product supply limits; the request allowlist, single-account lock, single transport, request ledger, pacing, circuit breaker, and manual recovery remain mandatory.

Recruiter favorite-list sync is the only list flow allowed beyond search page 2. It uses only the safe client's fixed `bossGetGeek` endpoint with fixed `tag=4`, a pre-authorized page manifest capped at 40 pages, existing random list pacing, and strictly serial GETs with no retry. Initialization is complete only at list end; incremental sync is complete only at the prior ordered first-page anchor or list end. A cap, malformed response, business failure, or risk remains incomplete and cannot authorize favorite writes. Sync and favorite delivery require separate human runs and authorizations.

The account-level favorite registry and delivery ledger live under the fixed Git-common account namespace and never depend on a normal work/output directory. Registry keys are stable `encryptGeekId` values only, history is append-only, and publishing excludes registered candidates without search refresh or backfill. The normal favorite workflow freezes the complete eligible local ranking pool before sync without showing a temporary Top 5, binds the sync receipt to that immutable pool, and only after a complete sync freezes the highest-ranked unregistered Top 5 as an exact original-rank subset. A favorite delivery must consume the complete same-account, same-day, same-batch sync receipt and recheck the registry under lock before each write reservation; newly registered candidates are skipped without replacement after the final selection is frozen. The advanced published-batch flow keeps its existing exact-subset contract.

Each selected, still-unconfirmed candidate may use one fixed favorite POST followed by one exact candidate readback GET, strictly serial and only through the safe client. Confirm only `alreadyInterested == 1`, then register the stable ID. On `favorite_unknown`, failure, or risk, stop the whole batch without retry, list scan, search refresh, backfill, message, contact, remark, cancel, or any other write.

An explicit recovery batch may ignore local delivery history and may reopen only a prior `favorite_failed`, because that state records a definite server rejection. It must be a newly published immutable batch, use a new complete same-account/same-day/same-batch sync receipt and a new human confirmation, and still gets only one POST in that recovery run. `favorite_unknown` and `write_reserved` are never recoverable automatically.

The current safety contract and stop rules are in `docs/boss-safe-operation.md`. Any change to a live entry, endpoint, retry, budget, authorization, auth namespace, guard namespace, browser tool, or network path must update the architecture and harness tests before implementation is considered complete.
